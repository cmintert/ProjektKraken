# Styling and Theme Adherence

## The Problem
Hardcoded styling (e.g., inline QSS strings with fixed hex colors) inside individual UI widgets leads to inconsistencies and prevents the application from responding correctly to theme changes (like switching between Dark Mode, Light Mode, and Fantasy modes). Additionally, standard push buttons used in toolbars look like disjointed boxes rather than native, flat toolbar actions.

## The Solution
1. **Centralized Styling (`StyleHelper`)**
   All component-specific QSS must be generated within `src.gui.utils.style_helper.StyleHelper`. Instead of writing `Widget.setStyleSheet("...")` directly with hardcoded values, a new static method should be added to `StyleHelper` (e.g., `get_sheet_text_block_style()`). 

2. **ThemeManager Integration**
   `StyleHelper` dynamically reads the current active theme color palette using `ThemeManager().get_theme()`. This ensures all widgets instantly react to global theme updates if their `_apply_theme()` methods are connected to the `theme_changed` signal.

3. **Flat Toolbar Buttons vs Action Buttons**
   Always distinguish between standard action buttons (which need borders and solid backgrounds to indicate clickability) and toolbar buttons (which should blend into the toolbar panel).
   - Use `StyleHelper.get_tool_button_style()` for standard standalone buttons (`QPushButton`, `QToolButton` acting as a main action).
   - Use `StyleHelper.get_flat_tool_button_style()` for buttons residing within a `QToolBar` or a header row. This style makes the button transparent by default, only showing a background when hovered or pressed.

## Future Considerations
- When adding hover visual feedback (like highlighting an active row inside the Sheet Builder), utilize the `:hover` pseudo-class in the QSS generated by `StyleHelper` and map it to the theme's `primary` color.
- **NEVER** hardcode `#HEX` colors in widget classes. Rely entirely on the tokens provided by the active `theme` dictionary.
